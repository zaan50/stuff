package citi.interview.karat;

How the Karat round is structured

Karat is the third-party vendor Citi uses for the first technical screen. The exact questions vary, but the shape of the interview is consistent across candidate reports.

Rapid-fire Java theory (5–10 min)

5–6 quick concept questions — stack vs. heap, garbage collection basics, immutability, OOP fundamentals. Meant to be answered fast and precisely.

Code review / "spot the problem"

You're shown an existing Java class and asked to identify structural issues — thread-safety bugs, tight coupling, bad design choices.

Timed debugging exercise

A broken snippet or failing unit test (off-by-one errors, unhandled nulls) that you fix so it compiles and passes — often with a hard time box (~10–20 min).

Coding / implementation task

Write one or more methods from scratch — HashMap-based data processing and basic graph/BFS traversal are both reported. Some sessions instead run 2 LeetCode-style problems plus 6 rapid OOP-design questions plus 3 system-design scenarios.

Later rounds (post-Karat)

Once you clear Karat, actual Citi engineers/managers take over — project deep-dives, system design, and behavioral rounds.

Core Java & OOP fundamentals

The opening rapid-fire segment usually lives here. Give the textbook-precise answer first, then add nuance — Karat graders reportedly compare responses to a scripted answer key.

further reading → Oracle: Learning the Java Language · Java SE 17 API docs
Q1Explain the difference between an abstract class and an interface (post–Java 8).▸

Both let you define a type other classes can implement/extend, but they solve different problems:

  • Abstract class — can hold state (instance fields), constructors, and a mix of abstract + concrete methods. A class can extend only one abstract class.
  • Interface — since Java 8 it can have default and static methods with bodies, plus (Java 9+) private helper methods, but it still cannot hold instance state. A class can implement multiple interfaces.

Rule of thumb: use an interface to describe a capability/contract ("can fly", "can serialize"); use an abstract class when subclasses genuinely share implementation and state ("is a Vehicle with a fuel tank").

↗ Oracle Tutorial: Abstract Methods and Classes
Q2What is immutability, and how do you design your own immutable class?▸

An immutable object's observable state cannot change after construction — every "modification" returns a new instance instead (like String or LocalDate). Immutable objects are inherently thread-safe and safe to cache/share.

To build one:

  • Declare the class final so it can't be subclassed into a mutable variant.
  • Make all fields private final.
  • Set every field through the constructor only — no setters.
  • For mutable field types (collections, dates, arrays), do a defensive copy on the way in and on the way out.
public final class Money {
    private final BigDecimal amount;
    private final String currency;

    public Money(BigDecimal amount, String currency) {
        this.amount = amount;   // BigDecimal is itself immutable
        this.currency = currency;
    }
    public BigDecimal getAmount() { return amount; }
    public String getCurrency()   { return currency; }
    public Money add(Money other) {
        return new Money(this.amount.add(other.amount), currency); // returns new instance
    }
}
Q3What's the difference between == and .equals()?▸

== compares references for objects (are these two variables pointing at the exact same object in memory?) and values for primitives. .equals() is a method defined on Object that classes can override to compare logical equality — e.g. two different String objects holding "citi" are ==-unequal but .equals()-equal.

Gotcha: autoboxed Integer values between -128 and 127 are cached, so Integer a = 100, b = 100; a == b is true, but the same comparison at 200 is false — a classic Karat trick question.
Q4What happens if you override equals() but not hashCode() (or vice versa)?▸

You break the equals/hashCode contract: objects that are equal must return the same hash code. If you override only equals(), two "equal" objects can land in different hash buckets, so a HashSet/HashMap will treat them as distinct — duplicates silently get inserted, and lookups fail even though .equals() would say they match.

Always override both together (most IDEs and @EqualsAndHashCode from Lombok generate them as a pair for this reason).

↗ Object#hashCode() javadoc — general contract
Q5Method overloading vs. overriding — what's the difference?▸
  • Overloading — same method name, different parameter list, within the same class. Resolved at compile time (static/early binding).
  • Overriding — a subclass redefines a method with the same signature as its superclass/interface. Resolved at runtime based on the actual object type (dynamic/late binding, i.e. polymorphism).
Q6What are marker interfaces?▸

An interface with no methods at all — it exists purely to "tag" a class with metadata that other code can check via instanceof. Classic examples: Serializable, Cloneable, Remote. Modern Java tends to prefer annotations (@Deprecated, custom annotations) for this purpose, but marker interfaces still show up in legacy/serialization-heavy banking codebases.

Q7What is a record in Java 17?▸

A compact syntax for an immutable data-carrier class. The compiler auto-generates the constructor, private final fields, accessors, equals(), hashCode(), and toString() from the header — replacing a ton of DTO boilerplate.

public record TransactionEvent(String txnId, BigDecimal amount, Instant timestamp) {}
// usage: new TransactionEvent("T1", BigDecimal.TEN, Instant.now()).amount();
↗ Oracle: Records (Java 17 docs)
Q8What are virtual threads in Java 21?▸

Lightweight threads managed by the JVM instead of the OS (Project Loom). You can spin up millions of them cheaply because they're not each backed by a dedicated OS thread — when a virtual thread blocks on I/O, the JVM "parks" it and frees the underlying carrier OS thread to run something else. This lets you write simple blocking-style code (no reactive/callback pyramid) while still getting high throughput for I/O-heavy backend services — very relevant to a bank's high-volume transaction APIs.

↗ Oracle: Virtual Threads (Java 21 docs)
package citi.interview.jvm_memory;

JVM internals & memory management

"Stack vs. heap" is reported as one of the single most common opening questions in Citi's Karat round.

further reading → Oracle: Java Garbage Collection Tuning Guide
Q9Explain JVM memory structure — heap, stack, and metaspace.▸
  • Heap — shared across all threads; stores every object instance and array. Divided into generations (Young: Eden + Survivor spaces, and Old/Tenured) that the garbage collector treats differently based on object age.
  • Stack — one per thread; stores method call frames, local variables, and partial results. Grows and shrinks with method calls/returns; a runaway recursive call causes a StackOverflowError here, not on the heap.
  • Metaspace (replaced PermGen in Java 8+) — stores class metadata (method bytecode, field/method info). Lives in native memory rather than the heap, so it grows dynamically instead of hitting a fixed cap by default.
Q10What causes an OutOfMemoryError?▸

The JVM couldn't allocate memory it needed even after a full GC. Common flavors on a backend service:

  • Java heap space — too many live objects (memory leak, unbounded cache, huge result set loaded into memory).
  • Metaspace — too many classes loaded, often from a classloader leak (e.g. redeploying an app repeatedly without releasing old classloaders).
  • GC overhead limit exceeded — the JVM is spending >98% of time GC-ing and reclaiming <2% of heap — effectively thrashing.
  • Unable to create new native thread — you've exhausted OS-level threads/stack memory, usually from an unbounded thread pool.
Q11Difference between a heap dump and a thread dump.▸

A heap dump is a snapshot of every live object on the heap at a point in time — used to diagnose memory leaks (tools: Eclipse MAT, VisualVM; triggered with jmap or -XX:+HeapDumpOnOutOfMemoryError). A thread dump is a snapshot of every thread's current stack trace and state (RUNNABLE, BLOCKED, WAITING) — used to diagnose deadlocks, contention, and hung requests (tools: jstack, kill -3).

Q12Walk through GC algorithms: G1, CMS, ZGC.▸
  • CMS (Concurrent Mark Sweep) — deprecated since Java 9, removed in 14. Ran most of its work concurrently with the app to minimize pause time, but caused heap fragmentation over time.
  • G1 (Garbage First) — the default collector since Java 9. Splits the heap into equal-sized regions and prioritizes collecting the regions with the most garbage first, aiming for predictable pause-time targets. A solid general-purpose choice for most backend services.
  • ZGC — a scalable, low-latency collector (sub-millisecond pauses) that does almost all work concurrently, and scales to very large heaps (multi-TB). Chosen when pause-time predictability matters more than raw throughput — e.g. latency-sensitive trading/payment paths.
Q13What is a memory leak in Java, and how do you detect one?▸

Java is garbage-collected, but a "leak" still happens when objects stay reachable long after they're actually needed, so the GC can never reclaim them. Classic causes in backend code: static collections that only ever grow, listeners/callbacks that are registered but never unregistered, unclosed resources (connections, streams), and ThreadLocal values that outlive the request in a pooled-thread environment.

Detection approach: watch heap usage over time in monitoring (a sawtooth that never returns to baseline after GC is the signature); take heap dumps at two points in time and diff the dominant retained-size objects in Eclipse MAT; enable -XX:+HeapDumpOnOutOfMemoryError in production so you capture a dump automatically when it finally fails.

package citi.interview.collections;

Collections framework

How HashMap works internally is reported as one of the most consistently asked questions across every source.

further reading → Oracle: Collections Framework trail
Q14How does HashMap work internally?▸

HashMap stores entries in an array of "buckets". To find a bucket for a key: compute key.hashCode(), run it through an internal spreading function to reduce collisions, then take it modulo the array length. Each bucket holds a linked list of entries that hash to the same slot; on lookup, Java walks that list comparing keys with .equals() until it finds a match.

  • Load factor (default 0.75) — once the map is 75% full, it resizes (doubles capacity) and rehashes everything.
  • Java 8+ optimization — if a single bucket's linked list grows past 8 entries (and the table is large enough), that bucket converts into a red-black tree, turning worst-case lookup from O(n) into O(log n) for pathological hash collisions.
↗ HashMap javadoc (implementation notes)
Q15What problems does the Java Collections Framework solve?▸

Before it (pre-Java 2), every developer wrote ad-hoc array-based or linked-list data structures with inconsistent APIs. The Collections Framework gives a unified set of interfaces (List, Set, Map, Queue) with interchangeable, well-tested implementations, consistent iteration (Iterator/for-each), built-in algorithms (Collections.sort, binarySearch), and generics for compile-time type safety — reducing boilerplate and bugs across any codebase that needs to store and manipulate groups of objects.

Q16How does hashCode() affect HashMap performance?▸

A good hashCode() spreads keys evenly across buckets, keeping lookups close to O(1). A poor one — e.g. a constant hash code, or one that clusters heavily — pushes many keys into the same bucket, degrading that bucket's lookup toward O(n) (or O(log n) once Java 8's treeify kicks in, but that's still worse than a well-spread map). This is why overriding hashCode() carefully (combining all significant fields, e.g. via Objects.hash(...)) matters for any class you plan to use as a map key.

Q17ArrayList vs LinkedList, and HashMap vs TreeMap vs LinkedHashMap.▸
  • ArrayList — backed by a resizable array; O(1) random access, O(n) insert/remove in the middle (has to shift elements). Best default choice for most cases.
  • LinkedList — doubly linked list; O(1) insert/remove at the ends (great as a Deque/Queue), but O(n) random access. Rarely the right default in modern Java — ArrayList/ArrayDeque usually win due to cache locality.
  • HashMap — no ordering guarantee, fastest average-case O(1) get/put.
  • LinkedHashMap — HashMap plus a linked list tracking insertion (or access) order — useful for predictable iteration order or building an LRU cache via removeEldestEntry.
  • TreeMap — a red-black tree keeping keys in sorted order; O(log n) get/put, useful when you need firstKey()/ceilingKey()/range queries.
package citi.interview.functional;

Functional interfaces & Streams

Modern Citi backend teams write Spring Boot services with heavy Stream usage, so expect at least a couple of functional-style questions.

further reading → Stream javadoc
Q18What are Function, Consumer, and Predicate?▸

They're the core built-in functional interfaces in java.util.function, each describing a lambda shape:

  • Function<T,R> — takes a T, returns an R (apply(T)). e.g. mapping an Account to its balance.
  • Consumer<T> — takes a T, returns nothing (accept(T)). e.g. logging or sending each item somewhere.
  • Predicate<T> — takes a T, returns a boolean (test(T)). e.g. a filter condition like "is this transaction over $10,000".
  • (Related, often asked together) Supplier<T> — takes nothing, returns a T — for lazy value production.
Q19Walk through the Stream API — filter, map, collect.▸

A Stream is a lazy, one-pass pipeline over a data source. Intermediate operations (filter, map, sorted) are lazy and return a new stream; nothing actually runs until a terminal operation (collect, forEach, reduce, count) triggers the pipeline.

List<String> highValueTxnIds = transactions.stream()
        .filter(t -> t.amount().compareTo(THRESHOLD) > 0)
        .sorted(Comparator.comparing(Transaction::amount).reversed())
        .map(Transaction::id)
        .collect(Collectors.toList());

Know the difference between Collectors.toList(), toMap() (and its merge-function overload for duplicate keys), and groupingBy() — grouping transactions by account ID is a very plausible follow-up.

package citi.interview.concurrency;

Multithreading & concurrency

Reported as one of the heaviest-weighted topics — deadlocks, locking, and thread-safety code review show up across nearly every candidate report.

further reading → Oracle: Concurrency trail
Q20What conditions lead to a deadlock?▸

Four conditions must all hold simultaneously (Coffman conditions):

  • Mutual exclusion — a resource can only be held by one thread at a time.
  • Hold and wait — a thread holds one lock while waiting for another.
  • No preemption — a lock can't be forcibly taken away; it must be released voluntarily.
  • Circular wait — a cycle of threads exists where each waits on a lock the next one holds.

Classic example: Thread A locks accountX then wants accountY; Thread B locks accountY then wants accountX — neither can proceed.

Fix: always acquire locks in a consistent global order (e.g. always lock the account with the lower ID first), use tryLock with a timeout, or reduce lock scope.

Q21Write 3 threads that run in parallel but must finish in a specific order.▸

The cleanest modern approach is CompletableFuture chaining, which expresses the ordering declaratively instead of manually juggling locks:

CompletableFuture<Void> t1 = CompletableFuture.runAsync(() -> System.out.println("First"));
CompletableFuture<Void> t2 = t1.thenRunAsync(() -> System.out.println("Second"));
CompletableFuture<Void> t3 = t2.thenRunAsync(() -> System.out.println("Third"));
t3.join();

If the interviewer specifically wants raw Thread/join() usage instead: start Thread 1, call thread1.join() inside Thread 2 before it runs its own body, and thread2.join() inside Thread 3 — each thread blocks until its predecessor finishes. CountDownLatch is another idiomatic tool for this exact "wait for N things to finish before proceeding" pattern.

Q22Locks & synchronization: synchronized vs ReentrantLock vs concurrent collections.▸
  • synchronized — a built-in intrinsic lock on a method or block. Simple, automatically released even on exception, but inflexible (no timeout, no fairness policy, can't check if it's locked).
  • ReentrantLock (java.util.concurrent.locks) — explicit lock/unlock calls (needs a try/finally), but supports tryLock() with a timeout, interruptible locking, and fairness ordering — useful when you need more control than synchronized gives you.
  • Concurrent collections (ConcurrentHashMap, CopyOnWriteArrayList, BlockingQueue) — purpose-built thread-safe data structures that use fine-grained internal locking or lock-free algorithms, almost always faster and safer than wrapping a plain collection in your own synchronized blocks.
Q23Given a Java class, how do you spot thread-safety issues in a code review?▸

This is a reported live exercise — the checklist to narrate out loud:

  • Any mutable instance field that's read/written by multiple threads without synchronization? (e.g. a plain int counter incremented via counter++ — not atomic.)
  • Is the class supposed to be a singleton/shared bean? Look for lazy initialization without proper double-checked locking or a holder class.
  • Is a collection field (List/Map) exposed via a getter without returning an unmodifiable/defensive copy — allowing external threads to mutate it concurrently?
  • Compound actions that look atomic but aren't — e.g. "check if key exists, then put" on a plain HashMap is a check-then-act race condition; use ConcurrentHashMap.computeIfAbsent instead.
Gotcha: counter++ on a shared field is three separate operations (read, increment, write) — not atomic even though it looks like one line. Use AtomicInteger or synchronize.
Q24General multithreading + streams + locks + synchronization — what ties these together?▸

This combined theme (reported directly from a Citi review) is really testing whether you understand where parallelism is safe. A useful framing: prefer immutable data and higher-level constructs (streams, CompletableFuture, concurrent collections, the ExecutorService thread pool abstraction) over hand-rolled synchronized/wait/notify code, because manual locking is where deadlocks and race conditions creep in. Know that parallelStream() uses the common ForkJoinPool and is only safe/beneficial for CPU-bound, side-effect-free operations — not for I/O-bound work or anything touching shared mutable state.

package citi.interview.coding_tasks;

Hands-on coding & debugging tasks

The actual "write/fix code" portion. Karat graders reportedly weight a working, running solution over an elegant but incomplete one — get something compiling and passing tests first, then optimize if time remains.

Q25General strategy: how do you debug an unfamiliar broken Java class under time pressure?▸
  • Read before you touch anything. Narrate what the class/method is supposed to do in one sentence before diving in.
  • Reproduce first. Run the failing test/snippet and read the actual stack trace or assertion failure — don't guess.
  • Bisect. If it's a longer method, add print statements or use the debugger to isolate which line diverges from expected behavior.
  • Fix the smallest thing that makes it correct, then re-run to confirm, rather than rewriting the whole method.
  • State assumptions out loud — Karat interviewers are grading your process, not just the final diff.
Q26Fix a failing unit test caused by an off-by-one loop error and an unhandled null.▸

Two of the most common Karat-reported bug categories, worth having muscle memory for:

// Off-by-one: classic bug
for (int i = 0; i <= items.size(); i++) { // BUG: should be < not <=
    process(items.get(i));                 // throws IndexOutOfBoundsException on last iteration
}

// Fix:
for (int i = 0; i < items.size(); i++) {
    process(items.get(i));
}

// Unhandled null: classic bug
String status = order.getStatus().toUpperCase(); // NPE if getStatus() can return null

// Fix (defensive):
String status = Optional.ofNullable(order.getStatus())
                         .map(String::toUpperCase)
                         .orElse("UNKNOWN");
Q27Implement a HashMap-based data-processing task.▸

A representative version of this pattern — count/group items by a key using a Map, which is the shape most "HashMap data processing" prompts take:

// Group transactions by account and sum amounts
Map<String, BigDecimal> totalsByAccount = new HashMap<>();
for (Transaction t : transactions) {
    totalsByAccount.merge(t.accountId(), t.amount(), BigDecimal::add);
}

Map.merge() is worth knowing cold — it replaces the "check if key exists, then either put or add" boilerplate in one call, and interviewers notice when candidates know it.

Q28Implement a basic graph / BFS pathfinding algorithm.▸ 
public int shortestPath(Map<Integer, List<Integer>> graph, int start, int target) {
    Queue<Integer> queue = new LinkedList<>();
    Map<Integer, Integer> distance = new HashMap<>();
    queue.add(start);
    distance.put(start, 0);

    while (!queue.isEmpty()) {
        int node = queue.poll();
        if (node == target) return distance.get(node);
        for (int neighbor : graph.getOrDefault(node, List.of())) {
            if (!distance.containsKey(neighbor)) {
                distance.put(neighbor, distance.get(node) + 1);
                queue.add(neighbor);
            }
        }
    }
    return -1; // unreachable
}

Say out loud why BFS (not DFS) is correct here: BFS explores level-by-level, so the first time you reach the target is guaranteed to be via the shortest path in an unweighted graph.

Q29Write a program to rotate an array.▸

The O(n) time / O(1) extra space approach (reverse three times) is the one worth having memorized:

public void rotate(int[] nums, int k) {
    k %= nums.length;
    reverse(nums, 0, nums.length - 1);
    reverse(nums, 0, k - 1);
    reverse(nums, k, nums.length - 1);
}
private void reverse(int[] nums, int lo, int hi) {
    while (lo < hi) {
        int tmp = nums[lo]; nums[lo] = nums[hi]; nums[hi] = tmp;
        lo++; hi--;
    }
}
Q30Word-search / matrix traversal style problem — how do you approach it?▸

These are typically DFS-with-backtracking over a 2D grid. The pattern to reuse: try each starting cell, recursively explore up/down/left/right, mark cells visited on the way in and un-mark on the way out (backtrack), and bound your recursion with the target word's length or the grid edges.

Gotcha: a Blind reviewer specifically mentioned failing this exact style of problem for forgetting the "visited" bookkeeping — even when only right/down moves are allowed, without marking visited cells you can revisit a cell in the same path and get an infinite loop or wrong count.
package citi.interview.spring_boot;

Spring / Spring Boot / Microservices

Dominant in later technical rounds and for Senior/AVP-level candidates — Citi's Java backend job postings explicitly call out Spring Boot, microservices, Kafka, and REST/SOAP APIs.

further reading → Spring Framework · Spring Boot · Spring Security · Apache Kafka docs
Q31What is Dependency Injection, and how is it implemented in Spring?▸

Dependency Injection is a pattern where an object receives its collaborators from the outside instead of constructing them itself — decoupling "what a class needs" from "how that thing gets created," which makes code far easier to test (swap in a mock) and reconfigure.

Spring implements it via its IoC container: you declare beans (via @Component/@Service/@Repository + component scanning, or explicit @Bean methods in a @Configuration class), and Spring wires them together automatically:

@Service
public class TransferService {
    private final AccountRepository accountRepository; // dependency

    // Constructor injection — preferred: makes the dependency
    // explicit and required, and works well with immutability/testing
    public TransferService(AccountRepository accountRepository) {
        this.accountRepository = accountRepository;
    }
}

Constructor injection is generally preferred over field injection (@Autowired on a field) because it makes dependencies explicit, final, and easy to unit test without Spring even running.

Q32What is the Inversion of Control (IoC) container?▸

The IoC container is the part of Spring that owns the object lifecycle — it creates, configures, wires, and manages beans instead of your application code doing new everywhere ("inversion" of the normal control flow: the framework calls you, rather than you calling the framework). It's what actually performs the dependency injection described above, reading configuration from annotations, XML, or Java config classes.

Q33What are Spring bean scopes, and how are they set via annotations?▸
  • singleton (default) — one shared instance per Spring container. Watch out for mutable state here in a multi-threaded web app.
  • prototype — a new instance every time the bean is requested.
  • request / session — web-aware scopes, one instance per HTTP request or session (needs web-context).
@Service
@Scope("prototype")
public class ReportGenerator { ... }
Q34REST API design and versioning — what do you consider?▸
  • Resource-oriented URLs (/accounts/{id}/transactions, not /getAccountTransactions) and correct HTTP verbs (GET/POST/PUT/PATCH/DELETE) + status codes (200/201/400/404/409/500).
  • Versioning strategy — URL path (/v1/accounts), header-based, or media-type based; be ready to explain the trade-off (URL versioning is simplest to reason about but "pollutes" the resource identity).
  • Idempotency for retried requests (especially important in payments — a duplicate transfer request must not double-charge).
  • Consistent error response shape (e.g. RFC 7807 problem details) and pagination for large collections.
Q35Explain Spring Security with OAuth2/JWT at a high level.▸

Spring Security wraps every incoming request in a filter chain that authenticates and authorizes it before it reaches your controller. In a typical OAuth2/JWT setup: the client obtains a signed JWT access token from an authorization server (login, or client-credentials flow for service-to-service); on each request, a resource-server filter validates the token's signature and expiry, extracts claims (user identity, scopes/roles) into the SecurityContext, and your endpoints declare required roles via @PreAuthorize or security config rules. JWTs are self-contained and stateless, so any service instance can validate a request without a shared session store — important for horizontally scaled microservices.

Q36How do you build and secure microservices?▸
  • Boundaries — split by business capability (accounts, payments, risk-scoring), each owning its own data store, avoiding shared databases between services.
  • Communication — synchronous REST/gRPC for request/response needs; async messaging (Kafka) for events and decoupling — critical in banking where a payment posting shouldn't block on a downstream notification service being up.
  • Resilience — timeouts, retries with backoff, and circuit breakers (Resilience4j) so one slow downstream service doesn't cascade-fail the whole chain.
  • Security — mTLS or a service mesh for service-to-service traffic, token propagation (pass the caller's JWT downstream or use client-credentials for service identity), and an API gateway as the single ingress point enforcing auth, rate limiting, and routing.
Q37Kafka: producers, consumers, partitioning, and delivery guarantees.▸
  • Topic/partition — a topic is split into partitions for parallelism; Kafka guarantees order only within a partition, not across the whole topic. Choose your partition key (e.g. account ID) so related events land on the same partition and stay ordered.
  • Producer — writes messages; acks=all waits for all in-sync replicas to confirm before considering a write successful (safest, used for financial events).
  • Consumer group — each partition is consumed by exactly one consumer within a group, giving you horizontal scaling by adding consumers (up to the partition count).
  • Delivery guarantees — at-most-once (fire and forget), at-least-once (default with manual offset commit after processing — can duplicate on retry, so consumers must be idempotent), and exactly-once (Kafka transactions, more overhead) — banking event pipelines usually pick at-least-once + idempotent consumers over the complexity of exactly-once.
Q38CI/CD, Docker, and Kubernetes — what should you be able to speak to?▸

Be ready to describe an actual pipeline you've worked with, end to end: commit triggers a build → automated unit/integration tests run → a Docker image is built and pushed to a registry → deployment to Kubernetes (rolling update, readiness/liveness probes so traffic doesn't hit a pod before it's ready) → automated smoke tests → promotion through environments (dev → UAT → prod). Know what a readiness probe vs. liveness probe does, and why immutable, versioned container images make rollbacks trivial (redeploy the previous image tag).

Q39What cloud concepts should you know (AWS/GCP)?▸

You don't need deep cloud-specific expertise, but be comfortable discussing: compute (EC2/ECS/EKS or GCE/GKE — containers vs. VMs vs. managed Kubernetes), managed databases (RDS/Cloud SQL) vs. self-hosted, object storage (S3/GCS) for things like statement archives, IAM/least-privilege access for service credentials, and horizontal auto-scaling based on load. Citi job postings mention AWS, Azure, and GCP interchangeably, so frame answers around the underlying cloud concepts (elasticity, managed vs. self-managed, IAM) rather than one vendor's exact console.

Q40Testing methodology — unit vs. integration tests, mocking.▸
  • Unit tests — test one class/method in isolation, with collaborators mocked out (Mockito). Fast, run on every build.
  • Integration tests — test how components work together, often with a real (or containerized, via Testcontainers) database/message broker, verifying wiring and actual query behavior. Slower, run less frequently (e.g. pre-merge, not on every keystroke).
  • Mocking — replace a real dependency with a fake that returns canned responses, so you can test your class's logic without needing the real downstream service/DB. Know the difference between a mock (verifies interactions, e.g. "was save() called once") and a stub (just returns fixed data).
package citi.interview.sql_database;

SQL & Database

SQL questions are reported as a near-universal add-on at the end of the Java portion of the round, even in a "Java-focused" interview.

further reading → Oracle Database documentation
Q41DDL vs. DCL vs. DML — what's the difference?▸
  • DDL (Data Definition Language) — defines/alters structure: CREATE, ALTER, DROP, TRUNCATE. Most DDL auto-commits.
  • DML (Data Manipulation Language) — manipulates the data itself: SELECT, INSERT, UPDATE, DELETE. Transactional — can be rolled back.
  • DCL (Data Control Language) — controls access/permissions: GRANT, REVOKE.
Q42TRUNCATE vs. DELETE vs. DROP.▸
  • DELETE (DML) — removes rows one at a time, can use a WHERE clause, fires triggers, is logged row-by-row, and can be rolled back within a transaction.
  • TRUNCATE (DDL) — removes all rows by deallocating the data pages, no WHERE clause, doesn't fire per-row triggers, is much faster, and resets identity/auto-increment counters — but is minimally logged and typically can't be selectively rolled back the same way.
  • DROP (DDL) — removes the entire table structure itself (schema, indexes, constraints, data) — nothing is left behind.
Q43Design a small database schema (e.g. a library system) and write a query against it.▸

Reported almost verbatim in a Glassdoor review. A clean approach for any "design + query" prompt like this:

CREATE TABLE book (
    book_id     INT PRIMARY KEY,
    title       VARCHAR(200) NOT NULL,
    author      VARCHAR(150)
);
CREATE TABLE member (
    member_id   INT PRIMARY KEY,
    name        VARCHAR(150) NOT NULL
);
CREATE TABLE loan (
    loan_id     INT PRIMARY KEY,
    book_id     INT REFERENCES book(book_id),
    member_id   INT REFERENCES member(member_id),
    borrowed_on DATE NOT NULL,
    returned_on DATE
);

-- Books currently on loan (not yet returned)
SELECT b.title, m.name, l.borrowed_on
FROM loan l
JOIN book b   ON b.book_id = l.book_id
JOIN member m ON m.member_id = l.member_id
WHERE l.returned_on IS NULL;

Talk through your normalization choices out loud (why loan is a separate table rather than a column on book) — that reasoning is usually what's actually being graded, not just the final DDL.

Q44What should you know about PL/SQL and stored procedures?▸

Citi's Java Backend postings explicitly call out Oracle/PL-SQL, so for more senior/backend-heavy roles expect at least a conceptual question here: stored procedures bundle SQL logic that runs inside the database, reducing round trips for multi-step operations, enabling reusable business logic shared across applications, and allowing fine-grained GRANT EXECUTE permissions instead of exposing raw table access. Trade-off to mention: logic split between application code and stored procedures can become harder to version, test, and deploy compared to keeping business logic entirely in the Java service layer — a real architectural trade-off worth acknowledging rather than picking a side dogmatically.

package citi.interview.system_design;

System design & scenario questions

Reported as a distinct ~10-minute segment within Karat itself for some reqs, and as a full separate round for Senior/AVP candidates.

Q45How would you scale a service or reduce infrastructure cost for the company?▸

Structure the answer around where the cost/load actually comes from: measure first (is it CPU, memory, I/O, or database-bound?), then apply the matching lever — horizontal auto-scaling for bursty compute load, caching (Redis/local cache) for read-heavy hot paths to cut redundant DB hits, async processing (queue the work, respond fast) for anything that doesn't need a synchronous answer, connection pooling and query optimization/indexing for DB-bound services, and right-sizing over-provisioned instances. Close with how you'd verify the change actually helped — metrics before/after, not just theory.

Q46Walk through a production issue you've handled.▸

Use a structured narrative (STAR-like, but technical): what alerted you (metric/alarm/customer report) → how you triaged (logs, dashboards, thread/heap dumps if relevant) → root cause → the fix you shipped → what you changed afterward (a new alert, a test, a runbook) so it can't silently recur. Interviewers specifically listen for the "prevention" step — it signals seniority beyond just firefighting.

Q47Design for reliability and scale in a payments/lending-style scenario.▸

Given Citi's domain (Global Lending Services, Credit Platform, payments), a strong answer touches: idempotency keys so a retried payment request can't double-execute, an outbox pattern or transactional messaging so a DB write and an event publish stay consistent even if the service crashes mid-operation, clear consistency requirements (strong consistency for balance updates, eventual consistency acceptable for downstream notifications), and defense in depth against partial failures — timeouts, retries with exponential backoff, circuit breakers, and dead-letter queues for messages that repeatedly fail processing.

Q48Object-oriented design: design a small system (e.g. a text editor or the library system) using OOP principles.▸

Interviewers are checking whether you reach for the right OOP tools naturally: identify the core entities and their responsibilities (single responsibility principle), use interfaces for behaviors that will have multiple implementations (e.g. a Command interface for undo/redo in a text editor), favor composition over inheritance for "has-a" relationships, and keep mutable state encapsulated behind well-named methods rather than exposing raw fields. Sketch the class list and relationships out loud before writing any code — Karat/Citi interviewers reportedly value a clear plan stated up front.

Q49Describe your approach to finding bugs in an existing/unfamiliar codebase.▸

A recurring theme specific to Citi — they want to see how you operate in a large, inherited enterprise codebase, not just how you solve a fresh problem. A strong answer: start from the symptom (failing test, bug report, or stack trace) and work backward rather than reading the whole codebase top to bottom; use the debugger and logs before guessing; check recent commit history/blame for what changed near the affected area; write a failing test that reproduces the bug before fixing it, so you have a regression guard afterward; and communicate findings to the team rather than silently patching and moving on.

package citi.interview.behavioral;

Behavioral / fit questions

Usually appear in the recruiter screen and in later panel/onsite rounds rather than inside Karat itself. Citi engineers work closely with risk, compliance, and audit teams, so expect that theme to surface.

Q50Tell me about yourself / walk me through your resume.▸

Keep it to ~90 seconds and structure it around your trajectory, not a chronological list: where you started technically, the thread connecting your roles (e.g. "I've spent my career on high-throughput backend systems"), and why that leads naturally to this role at Citi. End on the present — what you're doing now and what you're looking for next — so it flows into "why this role" without a separate abrupt pivot.

Q51Why Citi? Why this role specifically?▸

Avoid generic "it's a big respected bank" answers. Anchor on something specific: the scale of the systems (200M+ customer accounts, 160+ countries — genuinely hard distributed-systems problems), the specific domain of the team you're interviewing for (lending, payments, risk tech), or a concrete piece of Citi's engineering culture from the job description that matches what you want next (e.g. modernization work, AI-assisted engineering tooling mentioned in current postings). Specificity signals you actually read the JD rather than mass-applying.

Q52Tell me about a time you worked in a team, handled conflict, or met a tight deadline.▸

Use STAR (Situation, Task, Action, Result) and pick a story where you drove the resolution — not one where the conflict simply resolved itself. For conflict stories specifically, banks tend to listen for how you disagreed constructively (brought data, proposed alternatives) rather than either capitulating or escalating unnecessarily — fitting a regulated environment where process and documentation matter.

Q53What's your motivation for working in fintech/banking specifically?▸

You don't need a finance background — Citi's own guidance is explicit that prior banking experience isn't required for most engineering roles. A genuine answer usually centers on the engineering challenge (correctness and reliability actually matter — a bug can mean real money moving incorrectly, at real scale) or the stability/impact of building infrastructure that underpins a huge number of people's financial lives.

Q54How do you handle ownership and working with risk/compliance/audit stakeholders?▸

A recurring Citi-specific theme given the regulated environment. Strong answers describe treating compliance/risk partners as collaborators early in design (not a gate you hit at the end) — e.g. baking in audit logging, data governance, and traceability requirements into a feature's design from day one rather than bolting them on before a release. Mention a concrete habit: writing clear documentation, flagging risk trade-offs transparently in design reviews, and escalating control issues rather than quietly working around them.

package citi.interview.notes;

Patterns worth knowing before you go in

Not pure LeetCode. Multiple experienced-hire reviewers say Citi's Java round leans toward practical/production Java — debugging real-looking code, Spring internals, concurrency — over pure DSA grinding, though basic array/graph/hashmap problems still show up.
Karat graders work off a script. Several unrelated reports (not just Citi) note interviewers compare your answer to a pre-written expected answer. Practice giving the clean, standard textbook explanation first, then add nuance.
Communicate out loud. The interviewer is largely there to observe and record, not to help or hint — narrate your thought process throughout.
Time-box yourself. Debugging tasks have reported hard cutoffs (~20 min for a bug set). Don't over-polish one fix at the expense of finishing the set.
The bar may exceed your title. A few candidates felt the round was calibrated to ~6 YOE even when they had less — prep as if for the senior band regardless of your exact level.
Outcomes are genuinely mixed. Glassdoor/Fishbowl/Blind show both rejections and passes at similar experience levels; overall difficulty sits around 2.8–3.1/5 with ~67–70% positive candidate sentiment for the Java Developer / Senior Java Developer track.

One honest caveat

Karat and Citi periodically rotate their question banks, and multiple sources note the format varies by team, req level, and location (India vs. US vs. Poland rounds were all described somewhat differently). Treat this page as a strong directional study guide — not a guaranteed leak of your exact question set.
